# Recipe brief: ai-suggestions

**One-liner:** Human-in-the-loop AI as document state: an agent writes suggestions
into the document via ordinary operations, humans resolve each one
(ACCEPTED/DISMISSED), and the whole exchange lives in the audit log.

## Why this recipe

This is the most architecturally distinctive pattern in the registry survey: Vetra
Studio embeds an `agentFeedback` block in *every* spec document model, so AI
suggestions are event-sourced data with full provenance — not chat ephemera. It
demonstrates how Powerhouse's operation log naturally gives AI collaboration an audit
trail, and it composes with reducer-level rules (resolution immutability, optional
signer checks for agent identity).

## What it demonstrates

- Modeling AI feedback as document state: `{ readyForFeedback, suggestions[] }` with a
  per-suggestion resolution lifecycle.
- An agent loop that reads document state and dispatches `addSuggestion` operations.
- Reducer-enforced rules: can't resolve a nonexistent or already-resolved suggestion;
  resolutions are immutable.
- Replay safety with a nondeterministic producer: LLM output enters as operation
  input, so replay never re-calls the model.
- Optional: gating the `addSuggestion` operation to the agent's identity via
  `action.context.signer` (ties into `role-based-auth`).

## Suggested shape

Standalone package `@powerhousedao/example-ai-suggestions`.

- Document model: a "draft" document — `{ title, body, agentFeedback:
  { readyForFeedback, suggestions[] } }` with operations:
  - `setBody`, `requestFeedback()` (sets `readyForFeedback = true`),
  - `addSuggestion({ id, agent, content })`,
  - `resolveSuggestion({ id, decision, comment?, changeApplied? })`,
  - optionally `applySuggestion` as a compound op that both accepts and edits `body`.
- Reducer rules (the testable core): `addSuggestion` only when `readyForFeedback`;
  `resolveSuggestion` fails on unknown id or non-null resolution; resolving the last
  open suggestion clears `readyForFeedback`.
- `agent.ts` — watches for `readyForFeedback` (subscription like
  `cross-document-reactor`, or a simple poll), generates suggestions, dispatches
  `addSuggestion`. Two producer modes:
  - deterministic rule-based stub (e.g. flags passive voice / TODO markers) so the
    demo runs offline,
  - real Claude call behind `ANTHROPIC_API_KEY` (reuse the injection-friendly client
    shape from the `llm-extraction` brief).
- `demo.ts` — full cycle: author writes body → requests feedback → agent adds two
  suggestions → human accepts one (with `changeApplied`) and dismisses the other →
  print final state and the operation history showing the complete provenance chain.
- Tests: reducer rules above, plus replay determinism (re-reduce the op log → same
  state, agent never re-invoked).

## Implementation notes & pitfalls

- **Suggestions are data, not side effects.** The agent's nondeterminism is quarantined
  at the edge; everything in the document is replayable. Make this the README's thesis.
- Resolution immutability matters for trust: a dismissed suggestion must stay
  dismissed in history even if a similar one is added later (new id).
- If `applySuggestion` both accepts and mutates content, do it as ONE operation (atomic
  in the log) or two explicitly ordered ops — discuss the tradeoff; vetra records
  `changeApplied` on the resolution.
- Agent identity: populate `agent` from config, and optionally enforce via signer
  context in the reducer — point at `role-based-auth` for the mechanics instead of
  re-implementing.
- Keep ids ULID/uuid-generated by the dispatcher, not the reducer (determinism).
